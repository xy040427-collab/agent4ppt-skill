# 从材料到交付的工作流

本文件用于整套制作、恢复中断项目或调整用户参与程度。命令中的 `A4P` 代表入口脚本，不是要求用户自行安装的别名。

## 选择推进方式

用户希望共同设计时，依次展示大纲、风格方向和一张代表性样张，在这些决策得到答复后再批量生成。用户已经给出风格或参考材料，就直接提炼已有选择，不重新提供无关选项。用户说“直接给成品”意味着可以自行决定常规设计细节，但不意味着可以更换到新的付费服务、发布到外部网站或扩大素材使用范围。

将重要决定写入项目中的 `decisions.md`：受众、用途、时长、页数、语言、比例、风格、后端、是否需要样张确认、是否授权并行执行。它是人的决策记录，不能替代数据库状态。不要把用户授权自行设计记录为“用户亲自看过并认可每页”。

## 阶段与证据

| 阶段 | 需要完成的事 | 可检查的结果 |
|---|---|---|
| 整理材料 | 阅读来源、提取可用图、区分事实与假设 | 来源清单、素材、待解决问题 |
| 确定故事 | 每页回答一个问题，安排证据与转折 | `outline.md`，包含素材到页的映射 |
| 确定视觉 | 风格配方、标题层级、图像语言和输出方式 | `brief.json` 与决策说明 |
| 试做样张 | 选择能暴露真实难点的内容页 | 实际页面图片及检查记录 |
| 正式制作 | 领取页面、调用图片工具、登记结果 | 数据库事件、请求文件与图片 |
| 修复与备注 | 检查所有页、修订问题页、编写讲稿 | 完成状态、修订记录、`notes.md` |
| 导出交付 | 导出并用独立工具重新打开 | PPTX、预览、验证结论 |

只把已产生证据的阶段标为完成。API 接收任务不等于图片完成，图片文件存在不等于视觉检查完成，数据库显示完成也不等于已经验证 PPTX 能被读取。

## 草稿与变更

需要等待用户确认时，大纲和候选风格可以先写为草稿。不要在尚未确定素材映射时把不相关的图当成正式页面内容。得到调整意见后，更新大纲及对应页面规格，通过 `revise` 新建修订；不要直接修改 SQLite，也不要仅修改 `status.json`。

初始化后的 `brief.json` 是留档副本，数据库保存运行规格。直接编辑该 JSON 不会改变运行任务。单页修改用 `revise --page-file`；全局风格、后端或整套结构发生重大变化时，建立新项目并显式复用合适的资产。

## 进度与阻塞

向用户说明完成页数、正在处理的页和具体问题，而不是不断重复流程。对错误说明所处环节：输入缺失、工具不可用、服务失败、视觉不合格或文件导出失败。工具不可用时保留已有工作；不得偷偷生成本地占位页面后当成图像模型成品。

并行是可用的执行模式，不是质量保证。宿主支持且授权并行时按照 [页面执行](production.md) 分派；无并行能力时可以顺序完成，除非用户明确把并行当成任务条件。不要为了实现并发创建未经用户要求的新聊天任务。

## 完成条件

所有计划页都有可读图片，所有重要内容有来源或标明假设，备注与最终图片一致，导出的页面数和顺序正确，独立检查已完成或限制已明确披露。预览链接必须指向实际生成的预览，不把源图片列表描述成已运行的 PPT 渲染。
