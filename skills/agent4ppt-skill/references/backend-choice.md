# 图片生成路径的选择

## 内置工具优先的含义

检查当前会话实际可调用的图片生成工具。宿主名称、账户订阅或另一个会话曾经可用，都不能证明当前工具可用。Python `doctor` 也无法检测宿主工具列表。

如果当前有合适的内置工具，直接用它完成用户授权的图片任务。要求高分辨率、指定保存位置或批量制作，本身不构成更换 API 的理由。内置工具实际暴露什么参数，就按其文档传递什么参数；不要宣称底层使用某个无法观察的模型。

## API 适用情况

用户明确指定 API 或服务商、内置工具缺失，或已验证内置工具不能提供必需能力时，可以采用 API。涉及新凭据、计费账户或不同的数据接收方时，先解决相关选择，不能把用户同意做 PPT 理解为同意任意外部服务。

已有内置工具且任务能完成时，不要先让用户配置 API key。已经选定 API 后检查本地配置；配置错误再读 [环境与凭据](configuration.md)。`doctor --check-api` 只能辅助判断连接，不是完整生图测试。

## 整套一致与真实记录

项目固定 `builtin`、`openai` 或 `atlascloud` 后端。每页请求携带这个选择，`complete` 拒绝其他后端标签；带有生成方式约束的请求还会核对工具、模式和已记录的参数。记录是调用方提供的证据，CLI 无法独立证明宿主真的执行了那次工具调用。

不要因为某页包含截图就切后端，先检查同一路径的多参考图或编辑能力。所有需要的图片都必须实际附加；只在提示词中写文件名不算传图。后端无法接收所需图片时应报告具体能力缺口，而不是根据文字重新想象一张相似图片。

## 失败后的处理

区分工具暂时不可用、配额不足、参数不支持、认证失败和视觉不合格。只有后两者修复正确配置或内容后才重试。避免自动跨服务重试，因为这可能改变成本、数据接收方和风格。对提交后超时的远程任务，先查询已有任务结果，避免重复付费。

在开始生成时简短说明选择及原因即可；用户已经明确授权该方式时不重复询问。若用户指定逐阶段确认，则在第一张实际生成前完成该确认。
