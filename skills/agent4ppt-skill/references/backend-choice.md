# 图片生成路径的选择

## 内置工具优先的含义

检查当前会话实际可调用的图片生成工具。宿主名称、账户订阅或另一个会话曾经可用，都不能证明当前工具可用。Python `doctor` 也无法检测宿主工具列表。

如果当前有合适的内置工具，直接用它完成用户授权的图片任务。要求高分辨率、指定保存位置或批量制作，本身不构成更换 API 的理由。内置工具实际暴露什么参数，就按其文档传递什么参数；不要宣称底层使用某个无法观察的模型。

## 内置图片产物交接

完整成图和图片模型去字都需要执行本节。工具返回的展示用 `image_url` / data URL 不代表图片只在内存中。在 Codex 中，内置图片工具通常同时保存到 `$CODEX_HOME/generated_images/`（未设置时为 `~/.codex/generated_images/`）；以当前图片工具文档和实际输出为准，其他宿主不一定使用此目录。

1. 调用前记录任务、页码、阶段，以及本次输出目录已有文件清单。优先使用工具明确返回的本地路径或调用标识对应文件。恢复中断任务时，核对该次调用记录。
2. 只有展示 data URL 时，检查工具自动保存目录。用调用标识、调用前后新增文件清单和图片内容确认归属；并行调用必须分别关联，不能直接挑整个目录中最新图片。如果仍有多个候选，比较工具返回图片的解码字节 SHA-256；无法确定就报告“无法关联本次输出”，不要猜测或使用旧图。
3. 用 `A4P import-image --source <本次输出的绝对路径> --out <任务目录/page-001-design.png>` 原样导入；去字结果使用独立文件名。若已取得工具输出的哈希，附加 `--sha256 HASH`。命令校验图片可解码、返回尺寸和 SHA-256、拒绝覆盖已有文件，不选择图片、不进行生成、不推进状态。哈希只验证字节，不证明生成来源或视觉质量。
4. 查看导入图片并执行原有验收：完整成图走 `record-design`，去字图走 `record-background`，full-slide 模式走原有 `complete`。仍需有效 lease/token、方法记录与对应 QA；导入成功不能代替这些步骤。

确实没有本地文件、只有 data URL 时，用能持有工具返回对象的宿主文件 API 解码写文件，例如 Node 的 `fs.writeFile(path, Buffer.from(base64, 'base64'))`；再导入校验。不要把大段 Base64 打印到对话、拼接进 shell 命令或通过 Windows PTY/stdin 手动传输。若宿主既不保存文件也不能将返回字节写盘，报告该具体能力缺口，不能据此跳过去字或改用无关旧底图。

## API 适用情况

用户明确指定 API 或服务商、内置工具缺失，或已验证内置工具不能提供必需能力时，可以采用 API。涉及新凭据、计费账户或不同的数据接收方时，先解决相关选择，不能把用户同意做 PPT 理解为同意任意外部服务。

已有内置工具且任务能完成时，不要先让用户配置 API key。已经选定 API 后检查本地配置；配置错误再读 [环境与凭据](configuration.md)。`doctor --check-api` 只能辅助判断连接，不是完整生图测试。

## 整套一致与真实记录

项目固定 `builtin`、`openai` 或 `atlascloud` 后端。每页请求携带这个选择，`complete` 拒绝其他后端标签；带有生成方式约束的请求还会核对工具、模式和已记录的参数。记录是调用方提供的证据，CLI 无法独立证明宿主真的执行了那次工具调用。

不要因为某页包含截图就切后端，先检查同一路径的多参考图或编辑能力。所有需要的图片都必须实际附加；只在提示词中写文件名不算传图。后端无法接收所需图片时应报告具体能力缺口，而不是根据文字重新想象一张相似图片。

## 失败后的处理

区分工具暂时不可用、配额不足、参数不支持、认证失败和视觉不合格。只有后两者修复正确配置或内容后才重试。避免自动跨服务重试，因为这可能改变成本、数据接收方和风格。对提交后超时的远程任务，先查询已有任务结果，避免重复付费。

在开始生成时简短说明选择及原因即可；用户已经明确授权该方式时不重复询问。若用户指定逐阶段确认，则在第一张实际生成前完成该确认。
